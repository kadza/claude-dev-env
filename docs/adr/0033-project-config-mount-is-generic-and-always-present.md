# Project config mount is a generic, always-present template mount

Both templates' `devcontainer.json` always carry one mount line — `source=${localEnv:PROJECT_CONFIG_DIR},target=${localEnv:PROJECT_CONFIG_DIR},type=bind` — rather than a bespoke line added to a single project's `.devcontainer/devcontainer.json` when `--project-config` is first used. `d up --rebuild` wholesale-overwrites a project's `.devcontainer/` from its matching template (`cp -R .../templates/$tech/.devcontainer/. $PROJECT/.devcontainer/`), so any ad hoc per-project mount edit would be silently destroyed on the very next rebuild. Using the same absolute path as both `source` and `target` (mirroring the existing `workspaceMount` git-worktree trick) means a symlink into `PROJECT_CONFIG_DIR` resolves identically whether read from the host or from inside the container, without hardcoding a container-side path — necessary because the two templates run as different container users (`node-ts` → `/home/node`, `python` → `/home/vscode`). Because the mount is static and unconditional, `PROJECT_CONFIG_DIR` must always resolve to something that exists even when `--project-config` is never used, so `seed.sh`/`clone.sh`/`up.sh` all export it as a fixed, global, always-empty placeholder directory (`mkdir -p`'d unconditionally) whenever the flag is omitted. Rejected: patching the specific project's own `devcontainer.json` only when `--project-config` is first supplied — avoids the empty-mount-by-default cost, but gets silently wiped by the next `--rebuild` and requires remembering to re-supply the flag on every rebuild just to keep the mount alive.
